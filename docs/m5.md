# **M5 — Temporal Behaviour Estimation (Part B)**

Think of M4 and M5 this way:

- **M4 looks at one frame:** Is a person visible? Is their face visible? Are they inside the interaction zone? Are they facing the robot?
- **M5 looks at multiple frames over time:** Is the person approaching? Are they moving? Have they stopped? Have they remained stable for two seconds?

M5 does not need to understand what a person is thinking. It needs to understand how their position and behaviour change over time.

For example, imagine a person walking towards the reception robot:

1. Initially, the person is far from the interaction zone.
2. They move closer over several frames.
3. They enter the interaction zone.
4. They stop walking.
5. They remain there for two seconds.

M5 should detect and report these events using timestamped observations.

## **1. What additional things do we need?**

The good news: **we probably do not need another deep-learning model for M5.** Most of M5 can be implemented using the tracking information from M3 and observations from M4, combined with mathematical calculations over time.

### **A. Existing components we can reuse**

| Component           | What it gives M5                                                   |
| ------------------- | ------------------------------------------------------------------ |
| M3 tracker          | A person's bounding box and persistent track ID                    |
| M3 Kalman filter    | Smoothed position and estimated movement                           |
| M4 person detection | Whether the person was actually detected in the current frame      |
| M4 interaction zone | Whether the complete bounding box is inside the configured polygon |
| M4 face orientation | Whether the person appears to face the robot                       |
| Frame timestamps    | When each observation happened                                     |

M5 should consume these outputs rather than build another person detector or tracker.

**1. Position and trajectory calculation**

Record where the person is in each frame. For example, use the centre of the bounding box:

\\[ c_t=(x_t,y_t) \\]

Connect these positions over time to understand the person's path.

**2. Movement direction and speed**

Compare positions at different timestamps.

\\[ v_t=\frac{c_t-c\_{t-\Delta t}}{\Delta t} \\]

This tells us whether the person is moving and in which image direction.

**3. Approach detection**

Determine whether the person's movement is generally towards the reception interaction region, rather than simply moving sideways or away.

**4. Stationary detection**

If the person's position changes very little over a time window, classify them as stationary. Small camera or detector fluctuations should not count as real movement.

**5. Two-second stability timer**

Once the required conditions are continuously satisfied, start a timer. If the conditions break, reset or pause it according to the rule we decide.

### **C. Do we need additional ML models?**

My initial recommendation is:

No new ML model initially

| Approach                | Additional model? | Recommendation                           |
| ----------------------- | ----------------- | ---------------------------------------- |
| Position and trajectory | No                | Use bounding-box coordinates             |
| Velocity and direction  | No                | Use timestamp-based mathematics          |
| Approach detection      | No                | Start with geometric rules               |
| Stationary detection    | No                | Use displacement and velocity thresholds |
| Temporal smoothing      | No                | Use moving averages or hysteresis        |
| Two-second timing       | No                | Use timestamps                           |

A learned temporal model could be considered later if simple rules do not work reliably. I would not introduce an LSTM, GRU, Transformer, or another neural network before establishing a rule-based baseline.

## **2. How will M5 actually work?**

Here is a simple example of the processing sequence:

## **Example: person approaching and stopping**

1. **Person detected and tracked**

   M3 provides the track ID and bounding box. M4 provides the current observations.
2. **Store observations with timestamps**

   For example: position at 0.0 s, 0.1 s, 0.2 s, 0.3 s, and so on.
3. **Calculate movement**

   Compare recent positions to estimate speed and direction.
4. **Classify behaviour**

   Is the person approaching, moving in another direction, or stationary?
5. **Check temporal stability**

   Has the person continuously satisfied the required conditions for two seconds?
6. **Publish M5 observations**

   Provide approach, movement, stationary and stability-timer states, including uncertainty.

For example, the output might look like this:

| Time  | Behaviour                  |
| ----- | -------------------------- |
| 0–2 s | Moving towards reception   |
| 2–3 s | Entering interaction zone  |
| 3–4 s | Slowing down               |
| 4–6 s | Stationary for two seconds |

These are illustrative states, not a claim that the system will classify them correctly without testing.

## **3. What will the M5 software architecture look like?**

I would implement M5 as a separate temporal-processing module, not mix it into M3 or M4.

```
M3: Person Tracker
       |
       | Track ID, bounding box, timestamp
       v
M4: Frame-level Observations
       |
       | Zone, face, orientation, detection status
       v
M5: Temporal Behaviour Estimator
       |
       +--> Observation History
       |
       +--> Position & Trajectory Estimator
       |
       +--> Movement & Direction Estimator
       |
       +--> Approach Detector
       |
       +--> Stationary Detector
       |
       +--> Stability Timer
       |
       v
M5 Temporal Observation Output
```

Potential software modules:

| Module                   | Responsibility                                 |
| ------------------------ | ---------------------------------------------- |
| `observation_history.py` | Store recent timestamped observations          |
| `motion_estimator.py`    | Calculate displacement, velocity and direction |
| `approach_detector.py`   | Determine whether the person is approaching    |
| `stationary_detector.py` | Determine whether the person has stopped       |
| `stability_timer.py`     | Track continuous two-second stability          |
| `temporal_estimator.py`  | Coordinate the modules and produce output      |

These are proposed module names, not decisions about the final repository structure. We should follow its existing conventions.

## **4. What parameters will we need to configure?**

Unlike M4, M5 needs several time and movement thresholds.

| Parameter               | Meaning                                                                |
| ----------------------- | ---------------------------------------------------------------------- |
| History window          | How much previous movement to retain                                   |
| Velocity threshold      | Minimum movement considered meaningful                                 |
| Stationary threshold    | Maximum movement considered stationary                                 |
| Approach threshold      | How consistently movement must be towards the interaction region       |
| Smoothing window        | How much position fluctuation to smooth                                |
| Stability duration      | 2 seconds                                                              |
| Maximum observation gap | How long we tolerate missing observations before declaring uncertainty |

We should not guess these values. Start with reasonable configurable defaults, then tune them using recorded sequences.

## **5. Important limitation: laptop camera versus robot camera**

M5 will initially calculate movement in **image coordinates**, measured in pixels.

For example:

- Person moves from image position `(800, 300)` to `(700, 300)`.
- Their horizontal image displacement is 100 pixels.
- We can estimate image-space movement and direction.

But this does not mean the person physically moved a particular number of centimetres.

## **6. How should we test M5?**

We need labelled video sequences, not just unit tests.

For example, create short sequences representing:

| Test scenario                       | Expected behaviour                                          |
| ----------------------------------- | ----------------------------------------------------------- |
| Person walks towards reception      | APPROACHING                                                 |
| Person walks sideways               | MOVING, NOT APPROACHING                                     |
| Person walks away                   | MOVING AWAY                                                 |
| Person stops                        | STATIONARY                                                  |
| Person stands still for two seconds | Stability timer completes                                   |
| Person stops briefly, then moves    | Timer does not complete                                     |
| Person disappears temporarily       | Uncertainty handled explicitly                              |
| Tracker loses identity              | Old history must not be incorrectly assigned to a new track |

We should measure:

- Approach precision and recall.
- Stationary precision and recall.
- False approach detections.
- False stationary detections.
- Stability timer accuracy.
- Processing latency and FPS.

One important distinction: **unit tests verify the mathematics and timing logic; labelled sequences verify whether the behaviour estimator works on actual video.**

## **7. Decisions we should make before implementing M5**

I recommend that we finalize M5 through a few focused design discussions, just as we did for M4.

There are five particularly important areas:

1. **Position representation:** Should we track the bounding-box centre, bottom-centre, or both?
2. **Approach definition:** How exactly do we define movement towards the reception interaction zone?
3. **Stationary definition:** How much movement is acceptable before someone is considered to have stopped?
4. **Uncertainty handling:** What happens when detection or tracking is temporarily lost?
5. **Two-second timer:** Which conditions must remain continuously satisfied for the timer to complete?
